## 2. Versions shipped

**v4.9.1 · Fix: nightly backups silently dead for 18 days (BUG-015)**
- What: the Google Drive desktop app moved its mount from `~/Google Drive/My Drive` to `~/Library/CloudStorage/GoogleDrive-<account>/My Drive`, leaving the old path as an **empty stub**. `scripts/run-backup.sh` and `scripts/backup-data.mjs` both hardcoded the old path; `mkdir -p` recreated it on local disk, so the 2026-07-06 run wrote six tables into a folder Drive never synced, crashed on `manifest.json` (`ENOENT`), and the job then stopped producing output at all. Both scripts now probe `~/Library/CloudStorage/GoogleDrive-*/My Drive/mydesign` then the legacy path, and **abort with a logged error** rather than writing a backup nobody will ever read.
- Why: found while reading the Drive docs folder — `LATEST.txt` was 20 days stale and nothing had raised a flag.
- Schema: none. Tooling + docs only; no app code touched.
- Decision: PATCH under the v3.4.0 operational-backbone line. Fix the *class*, not the instance — a cloud-synced destination path is a moving target, so resolve it at runtime and fail loudly instead of hardcoding a new path that breaks identically next time.

## 4. Architectural decisions

- **Never hardcode a cloud-sync mount path.** Resolve it at runtime from the candidates that actually exist. Applies to any Drive-destined tooling (this pattern is shared with the PHSN and Favor Plus backup jobs — worth checking both).
- **A backup must fail loudly or not at all.** `mkdir -p` on a destination path is an anti-pattern for synced storage: it manufactures a plausible-looking local folder and converts a hard failure into a silent one. The script now refuses to run rather than produce an unreadable backup.
- **"Job is loaded" is not "job is working."** The health check now keys on `LATEST.txt`'s timestamp versus today, not on `launchctl list`.
