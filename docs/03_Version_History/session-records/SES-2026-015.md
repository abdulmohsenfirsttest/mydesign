## 4. Architectural decisions

- **Next.js 16 renamed Middleware to Proxy.** The file convention is `proxy.ts` at the repo root, it defaults to the **Node.js runtime**, and setting `runtime` throws. `AGENTS.md` instructs reading `node_modules/next/dist/docs/` before writing code, and that instruction paid for itself here — writing `middleware.ts` from memory would have produced a file Next 16 silently ignores.
- **The firewall is application code, not host configuration.** Vercel's WAF was the obvious route and was explicitly declined. Building it as `proxy.ts` means it travels with the repo if the site ever moves host, and it is reviewable in git rather than living in a dashboard nobody reads.
- **CSP must allow `'unsafe-inline'` for scripts in this codebase.** The anti-FOUC theme script in `app/layout.tsx` and Next's own inline bootstrap both require it. Removing it means a nonce refactor plus dynamic rendering on every page. Recorded as a known limitation rather than pretending the CSP stops inline-script XSS — it does not. It does stop external script loading, framing, off-site form posts, and exfiltration to any host that is not Supabase.
- **Form-level bot protection was rejected as security theatre in the current architecture.** Cloudflare Turnstile was requested. It cannot work here for two reasons and the second is fatal: there is no server-side code to verify a token against (0 API routes, 0 server actions, 0 proxy before this session), and more importantly the public anon key ships in the JS bundle while `bookings` and `clients` have no RLS policy, so a bot POSTs straight to the Supabase REST API and never loads the page. A widget on the form would stop nothing. The honest order is: edge filtering → move writes server-side → then Turnstile → then revoke anon INSERT.
- **Portfolio content model (proposed, not built):** a code-based content file rather than a database table. The photographs live in the repo, so changing one already requires a deploy; a CMS would not enable self-service while costing 2–3× the build. Shape it like a future table and route reads through one module so migrating later is an import plus a file swap.
